ข้อ 1 / 10บท 7 · Class Diagramพื้นฐาน–กลาง

วาด Class Diagram จากเรื่องที่ร้านเล่า

อ้างอิงหัวข้อ PDF อาจารย์: บท 7 หน้า 14, 17, 18 และ 25 · โจทย์นี้เป็นข้อสอบฝึกที่เรียบเรียงใหม่ ไม่ใช่ข้อสอบจริงของอาจารย์

1. สถานการณ์ที่โจทย์ให้มา

ร้านกาแฟมีสาขา แต่ละสาขามีพนักงานอย่างน้อย 1 คน พนักงานประจำอยู่สาขาเดียว คำสั่งซื้อหนึ่งรายการต้องมีรายการสินค้าอย่างน้อย 1 รายการ แต่ละรายการสินค้าชี้ไปยังสินค้าหนึ่งชนิด และสินค้าเดิมปรากฏในหลายออเดอร์ได้

2. สิ่งที่ต้องวาดและเขียนตอบ (20 คะแนน)

วาด UML Class Diagram ของ BRANCH, EMPLOYEE, ORDER, ORDER_LINE และ PRODUCT โดยเขียน Attribute อย่างน้อยคลาสละ 2 ตัว พร้อมความสัมพันธ์และ Multiplicity โดยใช้ Aggregation ระหว่างสาขากับพนักงาน และ Composition ระหว่างออเดอร์กับรายการสินค้า

3. คำถามตั้งต้นก่อนลงมือวาด

  1. เริ่มจากขีดชื่อ “สิ่งที่ต้องเก็บข้อมูล” จากเรื่องเล่าก่อน
  2. คำว่า “สาขามีพนักงานอย่างน้อย 1 คน” กลายเป็นตัวเลขอะไร
  3. วางเพชรกลวง/ทึบไว้ฝั่งใด เพราะเหตุใด
  4. อ่านความสัมพันธ์แต่ละเส้นจากสองทิศทางให้ครบ

4. ลองวาดเองบนกระดาน

ภาพบันทึกอัตโนมัติในเบราว์เซอร์ · มือถือสามารถเลื่อนกระดานแนวนอน

5. แผนภาพเฉลยตัวอย่าง (ขนาดใหญ่)

ทำจากโจทย์จนได้ภาพอย่างไร

  1. แยกคำนาม 5 คำให้เป็น Class (BRANCH, EMPLOYEE, ORDER, ORDER_LINE, PRODUCT) ไม่เอาคำกริยาเป็น Class
  2. BRANCH หนึ่งแห่งมี EMPLOYEE 1..* และ EMPLOYEE แต่ละคนอยู่ BRANCH 1 แห่ง จึงใช้เส้นพร้อมเพชรกลวงอยู่ฝั่ง BRANCH ตามกรณีในสไลด์
  3. ORDER หนึ่งรายการมี ORDER_LINE 1..* แต่ ORDER_LINE เป็นส่วนประกอบที่อยู่ภายใต้ ORDER เดียว จึงใช้เพชรทึบที่ ORDER
  4. PRODUCT หนึ่งชนิดถูกอ้างอิงโดย ORDER_LINE ได้ 0..* รายการ แต่แต่ละ ORDER_LINE อ้างอิง PRODUCT เพียง 1 ชนิด
  5. เพิ่ม Attribute ที่จำเป็น เช่น Branch_ID, Employee_ID, Order_ID, Line_No, Product_ID และตรวจทิศทางการอ่าน Multiplicity
จุดที่มักพลาด: ตัวเลขที่เขียนใกล้คลาสปลายทางหมายถึงจำนวนของคลาสปลายทางต่อวัตถุหนึ่งตัวอีกฝั่ง; เพชรต้องอยู่ฝั่ง Whole ไม่ใช่ Part.

6. เช็กงานวาดของตัวเอง

เกณฑ์ฝึกตรวจตัวเองที่สร้างขึ้นจากหัวข้อใน PDF ไม่ใช่เกณฑ์ให้คะแนนที่อาจารย์ประกาศไว้

ข้อ 2 / 10บท 7 · Class + CRCกลาง

วาด Generalization และ CRC Card

อ้างอิงหัวข้อ PDF อาจารย์: บท 7 หน้า 15, 19 และ 24–25 · โจทย์นี้เป็นข้อสอบฝึกที่เรียบเรียงใหม่ ไม่ใช่ข้อสอบจริงของอาจารย์

1. สถานการณ์ที่โจทย์ให้มา

ร้านรับเงินได้ 3 วิธี ได้แก่ เงินสด บัตร และ QR ทุกวิธีมีจำนวนเงิน วันเวลา และสถานะการชำระ แต่บางวิธีมีข้อมูลเฉพาะ เช่น เงินทอน หมายเลขอ้างอิงบัตร หรือรหัสธุรกรรม QR นอกจากนี้คำสั่งซื้อมีหน้าที่คำนวณยอดรวม ตรวจการชำระเงิน และส่งรายการเพื่อตัดสต็อก

2. สิ่งที่ต้องวาดและเขียนตอบ (20 คะแนน)

วาด Class Diagram แสดง PAYMENT เป็น Superclass และ CASH_PAYMENT, CARD_PAYMENT, QR_PAYMENT เป็น Subclass พร้อมเขียน CRC Card หนึ่งใบของ ORDER ระบุ Responsibility และ Collaborator

3. คำถามตั้งต้นก่อนลงมือวาด

  1. คุณสมบัติใดทุกวิธีจ่ายเหมือนกัน
  2. ข้อมูลใดเป็นของวิธีจ่ายแบบใดโดยเฉพาะ
  3. หัวสามเหลี่ยมของ UML ชี้ไปทางไหน
  4. CRC แยกหน้าที่ของคลาสกับคลาสที่ต้องร่วมงานได้หรือไม่

4. ลองวาดเองบนกระดาน

ภาพบันทึกอัตโนมัติในเบราว์เซอร์ · มือถือสามารถเลื่อนกระดานแนวนอน

5. แผนภาพเฉลยตัวอย่าง (ขนาดใหญ่)

ทำจากโจทย์จนได้ภาพอย่างไร

  1. รวบ Attribute ที่ใช้ร่วมกันไว้ใน PAYMENT เช่น paymentId, amount, paidAt, status
  2. แยกข้อมูลเฉพาะไปใน CASH_PAYMENT (change), CARD_PAYMENT (cardRef), QR_PAYMENT (qrTxnRef)
  3. ใช้เส้น Generalization ปลายสามเหลี่ยมกลวงชี้ขึ้นไปที่ PAYMENT เสมอ
  4. CRC ของ ORDER: Responsibilities ได้แก่ calculateTotal(), checkPayment(), sendToInventory()
  5. Collaborators คือ ORDER_LINE, PAYMENT และ CUSTOMER ตามสถานการณ์ที่ต้องทำงานร่วมกัน
จุดที่มักพลาด: Generalization ไม่ใช่ Association: อ่านว่า CASH_PAYMENT “เป็นชนิดหนึ่งของ” PAYMENT (is-a) ไม่ใช่ “มี” PAYMENT.

6. เช็กงานวาดของตัวเอง

เกณฑ์ฝึกตรวจตัวเองที่สร้างขึ้นจากหัวข้อใน PDF ไม่ใช่เกณฑ์ให้คะแนนที่อาจารย์ประกาศไว้

ข้อ 3 / 10บท 8 · ERDพื้นฐาน–กลาง

สร้าง ERD: ลูกค้าสมาชิกและลูกค้าทั่วไป

อ้างอิงหัวข้อ PDF อาจารย์: บท 8 หน้า 26–27 และ 31 · โจทย์นี้เป็นข้อสอบฝึกที่เรียบเรียงใหม่ ไม่ใช่ข้อสอบจริงของอาจารย์

1. สถานการณ์ที่โจทย์ให้มา

O-Wan Coffee รองรับลูกค้าทั่วไปที่ไม่ได้สมัครสมาชิก ออเดอร์หนึ่งรายการอาจไม่ผูกสมาชิก หรือผูกสมาชิกได้ 1 คน ส่วนสมาชิกหนึ่งคนอาจยังไม่มีออเดอร์ หรือมีออเดอร์ได้หลายรายการ ออเดอร์ทุกใบต้องอยู่ในสาขาเดียว แต่สาขาหนึ่งมีหลายออเดอร์ได้

2. สิ่งที่ต้องวาดและเขียนตอบ (20 คะแนน)

วาด ER Diagram ของ MEMBER, ORDER และ BRANCH ด้วย Cardinality ขั้นต่ำ/สูงสุด แล้ววาดตารางอย่างย่อแสดง PK และ FK ให้เห็นว่า ORDER.Member_ID เป็น NULL ได้ แต่ ORDER.Branch_ID ต้องมีค่า

3. คำถามตั้งต้นก่อนลงมือวาด

  1. เริ่มจากออเดอร์ 1 ใบ: ต้องมี MEMBER ไหม
  2. เริ่มจาก MEMBER 1 คน: ออเดอร์ขั้นต่ำและสูงสุดเท่าไร
  3. เริ่มจาก ORDER 1 ใบ: ต้องมี BRANCH ไหม
  4. ค่าที่ “ไม่บังคับ” ต้องสะท้อนที่ FK อย่างไร

4. ลองวาดเองบนกระดาน

ภาพบันทึกอัตโนมัติในเบราว์เซอร์ · มือถือสามารถเลื่อนกระดานแนวนอน

5. แผนภาพเฉลยตัวอย่าง (ขนาดใหญ่)

ทำจากโจทย์จนได้ภาพอย่างไร

  1. วาด MEMBER, ORDER และ BRANCH พร้อม Identifier ของแต่ละ Entity
  2. อ่านกฎ “ORDER อาจไม่มี MEMBER” เป็น ORDER→MEMBER 0..1
  3. อ่านกฎ “MEMBER ยังไม่ซื้อก็ได้” เป็น MEMBER→ORDER 0..N
  4. ORDER ทุกใบมี BRANCH 1 แห่ง: ORDER→BRANCH 1..1; BRANCH→ORDER 0..N (ถ้าสาขาเพิ่งเปิด)
  5. วาง Member_ID เป็น Nullable FK ใน ORDER และ Branch_ID เป็น NOT NULL FK ใน ORDER จากนั้นอ่านภาพย้อนกลับทีละทิศ
จุดที่มักพลาด: อย่าสลับความหมาย: 0..1 คือจำนวนสมาชิกต่อ 1 ออเดอร์ ไม่ใช่จำนวนออเดอร์ต่อ 1 สมาชิก.

6. เช็กงานวาดของตัวเอง

เกณฑ์ฝึกตรวจตัวเองที่สร้างขึ้นจากหัวข้อใน PDF ไม่ใช่เกณฑ์ให้คะแนนที่อาจารย์ประกาศไว้

ข้อ 4 / 10บท 8 · ERDกลาง–ยาก

เปลี่ยน M:N ให้เป็น ORDER_LINE พร้อม Key

อ้างอิงหัวข้อ PDF อาจารย์: บท 8 หน้า 22–23 และ 28–29 · โจทย์นี้เป็นข้อสอบฝึกที่เรียบเรียงใหม่ ไม่ใช่ข้อสอบจริงของอาจารย์

1. สถานการณ์ที่โจทย์ให้มา

ออเดอร์หนึ่งใบซื้อสินค้าได้หลายชนิด สินค้าแต่ละชนิดถูกซื้อซ้ำในหลายออเดอร์ โดยต้องเก็บจำนวน (Quantity), ราคาที่ขายจริงต่อหน่วย (Unit_Price) และลำดับรายการ (Line_No) ไว้กับรายการขายแต่ละบรรทัด

2. สิ่งที่ต้องวาดและเขียนตอบ (20 คะแนน)

วาด ERD ให้แก้ความสัมพันธ์ ORDER ↔ PRODUCT แบบ Many-to-Many ด้วย ORDER_LINE พร้อม PK/FK, Quantity, Unit_Price และระบุว่ากรณีนี้ ORDER_LINE มีลักษณะเป็น Associative Entity และเป็น Weak Entity ภายใต้ ORDER ได้อย่างไร

3. คำถามตั้งต้นก่อนลงมือวาด

  1. ความสัมพันธ์ ORDER กับ PRODUCT คือกี่ต่อกี่ หากยังไม่แยก LINE
  2. Quantity เป็นข้อมูลของ ORDER ทั้งใบหรือ PRODUCT ทั้งชนิด หรือ “คู่นั้น”
  3. ถ้า ORDER_LINE ต้องมี ORDER เสมอ คีย์ควรผูกกับอะไร
  4. ทำไม Order_ID เดียวเป็น PK ของ ORDER_LINE ไม่ได้

4. ลองวาดเองบนกระดาน

ภาพบันทึกอัตโนมัติในเบราว์เซอร์ · มือถือสามารถเลื่อนกระดานแนวนอน

5. แผนภาพเฉลยตัวอย่าง (ขนาดใหญ่)

ทำจากโจทย์จนได้ภาพอย่างไร

  1. เริ่มจาก M:N: 1 ORDER มีหลาย PRODUCT และ 1 PRODUCT อยู่หลาย ORDER
  2. แตกเส้น M:N โดยสร้าง ORDER_LINE คั่นกลาง และวาง Quantity กับ Unit_Price ใน ORDER_LINE
  3. กำหนด ORDER_LINE.PK = (Order_ID, Line_No), ORDER_LINE.Order_ID เป็น FK ไป ORDER และ Product_ID เป็น FK ไป PRODUCT
  4. ORDER→ORDER_LINE = 1..N และ LINE→ORDER = 1..1; PRODUCT→LINE = 0..N และ LINE→PRODUCT = 1..1
  5. บอกความต่าง: Associative แก้ M:N และเก็บข้อมูลของความสัมพันธ์; Weak ในโมเดลนี้ระบุบรรทัดด้วย Owner Key (Order_ID) ร่วมกับ Partial Key (Line_No)
จุดที่มักพลาด: ไม่ควรเก็บรายการสินค้าเป็นข้อความรวมใน ORDER ช่องเดียว; PK(Order_ID, Line_No) เป็นตัวอย่างการออกแบบหนึ่งที่ตอบกฎนี้ได้.

6. เช็กงานวาดของตัวเอง

เกณฑ์ฝึกตรวจตัวเองที่สร้างขึ้นจากหัวข้อใน PDF ไม่ใช่เกณฑ์ให้คะแนนที่อาจารย์ประกาศไว้

ข้อ 5 / 10บท 8 · EER Diagramกลาง

วาด Supertype/Subtype พร้อมข้อบังคับ

อ้างอิงหัวข้อ PDF อาจารย์: บท 8 หน้า 30–32 · โจทย์นี้เป็นข้อสอบฝึกที่เรียบเรียงใหม่ ไม่ใช่ข้อสอบจริงของอาจารย์

1. สถานการณ์ที่โจทย์ให้มา

องค์กรเก็บบุคคลใน PERSON คนหนึ่งอาจเป็น EMPLOYEE, MEMBER หรือทั้งสองบทบาท และมีบางคนอยู่ในฐานข้อมูลแต่ยังไม่มีบทบาทใด (เช่น เพิ่งลงข้อมูลติดต่อ) พนักงานมี Employee_No สมาชิกมี Point_Balance ขณะที่ทุกคนมี Person_ID, Name และ Phone

2. สิ่งที่ต้องวาดและเขียนตอบ (20 คะแนน)

วาด EER Diagram แบบ Supertype/Subtype แล้วกำหนดว่าเป็น Partial หรือ Total และ Disjoint หรือ Overlap พร้อมให้เหตุผลจากตัวอย่างบุคคลที่เป็นทั้งพนักงานและสมาชิก

3. คำถามตั้งต้นก่อนลงมือวาด

  1. ข้อมูลไหนทุกคนต้องมี
  2. Person_ID ซ้ำอยู่ในตารางลูกทุกตัวหรือไม่
  3. การเป็นพนักงานแล้วสมัครสมาชิกได้ไหม
  4. บุคคลที่ยังไม่มีบทบาทอยู่ใน PERSON ได้หรือไม่

4. ลองวาดเองบนกระดาน

ภาพบันทึกอัตโนมัติในเบราว์เซอร์ · มือถือสามารถเลื่อนกระดานแนวนอน

5. แผนภาพเฉลยตัวอย่าง (ขนาดใหญ่)

ทำจากโจทย์จนได้ภาพอย่างไร

  1. วาด PERSON เป็น Supertype เก็บ Person_ID, Name, Phone
  2. วาด EMPLOYEE กับ MEMBER เป็น Subtype เก็บคุณสมบัติเฉพาะ
  3. Subtype อ้างอิง/สืบทอด Person_ID จาก PERSON (Identifier เดียวกัน)
